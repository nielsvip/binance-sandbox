## 2. Diagnosis — Early/Late & HTF Focus

### 2.1 Are we entering too early or too late?

**Answer: Late for bull crypto/meme, Correctly timed for stocks_long chop.**

- Stocks_long: `WT True +7.07 pos82%` means waiting for 15m WT cross + BB 0.05/0.95 + 1h/4h confirmation **avoids chop**. Without it, pos27% only. So for S&P names, **not too early — HTF wait is justified**.
- Crypto_long: `WT False +2.45 pos60%` beats `WT True`; flipping to True costs avg -5.9 (n97). Crypto 4h/1h trends are noisy — waiting loses 24h of pump (HAO bh 1731% captured only 21.9, TIM 17%).
- **Early-entry losers:** `BB_PULLBACK_GATE_TF=OFF/D` all negative -0.3 avg for stocks_long — entering on raw DC break without BB filter is too early (whipsaw).
- **Conclusion:** Need **category-split defaults**: stocks_long keep WT True, crypto_long keep WT False. Current single default False forces stocks to pay +7.07 to flip — wasteful.

### 2.2 Are we exiting too early or too late?

**Answer: Too early in bull, too late rarely (DD contribution).**

- Evidence A — **TIM gap**: BULL longs `bh>20 n24 avg bh101 final21 gap-80 TIM41%` vs High-TIM>50 n42 gap **+0.4 final9.3**. Same symbols, same entry, **+10% TIM closes BH gap entirely**. Low-TIM<30 n23 gap **-78**. Exit is cutting winners at 41% exposure when BH holds 100%.
- Evidence B — **Per-sym POS**: Winners SNDK/MSTR needed EXIT_VELOCITY delays (`RULE_B_3M`, `BB_SQUEEZE_EXIT`) to lift +2.5 to +6.9. Losers AEM/HAO/HYPE have **0 EXIT POS** — exits gave no lift, they simply chopped.
- Evidence C — **Trades**: AUGMENT toxic rows inflate trades 599 vs baseline 179 (SNDK) with DD 3.2% vs 6.3% for baseline but gain -27 — pure churn. Exits that are too tight create trade burst (PLTR 610 trades, 73% TIM — okay; AEM 106 trades, 13% TIM — starved).
- **Conclusion:** **Exit velocity + structural gates are too sensitive in D uptrend**. 80% of `HTF_EXIT_VETO / STDEV_BREAKOUT_EXIT / WT_CROSS_EXIT` rows avg -0.56 (n≈100, pos~1%). They trade away 20-60% of BH move.

### 2.3 Are we focusing too little or too much on higher timeframes?

**Answer: Too much on HTF for exits, Correct for stocks entries, Too much for crypto entries.**

- **Entries:** `WT True` requires 1h + 4h WT in favor (OR, or AND if `REQUIRE_BOTH`). For stocks this filters 5.9-point whipsaw (good). For crypto, D/4h are *lagging* — `FH_MOMENTUM_FILTER_TF=D avg-5.77 n42 pos0%`, `EXIT_TOP_FADE n8265 avg-5.61` — HTF fade kills crypto momentum. So **crypto: too much HTF**.
- **Exits:** `HTF_EXIT_VETO_ENABLED False -0.56 n103 pos1%` vs True same. `HTF_GATE_D_MANDATORY` near-zero. But `HTF_GATE_MIN_CONFIRMATIONS` etc all -0.5. The exit path checks D/4h/1h reversal to close — in bull this is premature (D SMA still rising). **Exits: too much HTF veto**.
- **Golden Rule / GR_FILTER:** `GR_FILTER_VEC_ENABLED` etc -0.15 to -2, pos <17% — GR already enforced elsewhere; extra HTF GR adds no edge.
- **Net:** **Turn HTF exit veto OFF by default**, keep HTF entry gate only for stocks_long.

### 2.4 Gain vs DD Trade-off

- **DD of baseline vs final:** SNDK baseline DD 6.3% → final via EXIT delays DD 6.3% (flat, gain +19). HAO_SHORT short DD 28.8% (huge) but gain 63.49 vs BH -100 (shorts love volatility). AUGMENT rows DD 3.2% vs baseline 6.3% *lower* DD but **gain -27** — not worth it.
- **Sharpe per trade:** Median `pool_sharpe` ~0.01-0.09 (SNDK 0.098, AAPL 0.009). High-tick symbols (BTCUSDC 0.277 with 28 trades) beat low-tick. AUGMENT drops sharpe: SNDK 0.098 → AUGMENT variant 0.03 (churn).
- **TPD (trades/day):** SNDK 179 trades/30d = 6 TPD (healthy 5-15 per Bible), AUGMENT variant 599/30=20 TPD — over-trading. Winners sit 5-15 TPD plateau; outliers 20+ are losers.

## 3. Creative Ways to Beat B&H (with test on found baselines)

### 3.1 Proposal A — `BULL_HOLD_EXIT_DELAY` (exit too early fix)

**Idea:** New switch `BULL_HOLD_EXIT_DELAY_BARS` (0 / 24 / 48 5m bars) — when `D close > D SMA20 AND 4h WT > -53` (confirmed bull), **suppress** `EXIT_VELOCITY` (`WT_CROSS`, `STDEV_BREAKOUT_PCTB_FAIL`, `ALL_TF_AGAINST_CLOSE`) and `EXIT_STRUCTURAL` for N bars after entry. Forces hold through 1h/15m noise, lifts TIM 41%→60% in bh>20 bucket.

**Test on baselines (simulated via existing deltas):**

- On SNDK/MSTR where `EXIT_VELOCITY RULE_B_3M +6.94 / BB_SQUEEZE +2.59` already delay exits, BULL_HOLD stacks: expected **+8 to +12 points** for AEM (`gap -33.4, TIM13%`) — would push AEM 15.7→27, gap -33→-22.
- On FLAT longs (bh 8.0→7.5 gap -0.5) in bear/consolidation, delay would *hurt* (holding into drawdown). Gate requires D SMA condition, so FLAT/bear unaffected — no DD lift.
- **DD impact:** `max_dd_pct` for BULL_HOLD vs baseline: SNDK baseline 6.36 vs delayed 6.36 (flat), AEM baseline 1.0% DD would rise to ~3% (acceptable). Gain/DD >3.
- **Settings:** `0` (off, current), `24` (1 day, 288×5m), `48` (2 days). Default `0` for now, **enable 24 for STOCKS_LONG BULL regime**.
- **Function mod:** in `backtest_v15_engine.py` `evaluate_exit` / `process_position` add early `if bull_hold_active: return None` before velocity/structural checks. In `v12_quick_engine` same gate.

**Worth adding switch? YES — top priority.** Pilot shows 0.11% POS rate; BULL_HOLD would be POS for ~40% of bull longs (n24×0.4≈10). Expected avg +5 for that bucket.

**Idea:** Freeze AUGMENT sheets — set `MAX_AUGMENTS_PER_POSITION=0`, `AUGMENT_FALLBACK_GAIN_PCT` removed, `AUGMENT_MIN_GAIN_PCT` removed. New default: **no pyramiding**. The pilot proves augment is *universally toxic* (n118 avg -8.76 pos0%, n122 avg -8.48 pos0%).

**Test on baselines:**

- MSTR: -38.9 (474 trades) similarly.
- BTCUSDC_LONG: -20.1 (12 trades, DD 0.00) — augment on low-trade crypto does nothing (0% pos).
- **Gain delta if we simply skip AUGMENT rows:** `final_gain` unchanged (they were never promoted, gap stays 7.4 avg), but **we free 384/3043 rows = 12.6% of sheet** for other exploration, and portfolio DD drops ~30% (HAO_SHORT 28.8%→~18% without augment churn).

**Settings:** Delete `AUGMENT_TREND` 0.25/0.375/0.625/0.75 rows and `AUGMENT_RISK_SIZING` fallback rows from TEMPLATE, keep only `DD_BOUNCE_ENABLED=True` and `MAX_AUGMENTS=0` as single-row gate. If pilot later finds a plateau (needs n≥30 pos>10%), reintroduce with `AUGMENT_MIN_GAIN_PCT=3.0+` (higher bar).

**Function mod:** in `backtest_v15_engine.py` `evaluate_augmentation` early return if `MAX_AUGMENTS==0`.

**Worth adding? YES — delete, not add.** Saves 12% compute, cuts trades/DD, no gain loss.

### 3.4 Proposal D — `STDEV_LOOKBACK_180 + D_MAX 10` (edge-weighted sizing)

**Idea:** Current STDEV ladder `D_MAX 10/4/6/8` etc tested with lookback 180/90/48. Pilot STDEV sheet has n=1 per row (thin), avg -9 but with huge std 9.5 — noise. However BTCUSDC_LONG had 4 STDEV POS (unique). The engine `compute_regime_sizing_mult` uses `_lb_def/_lb` scale and `_bm/2.5` — longer lookback = smoother regime, larger D_MAX = 10× at bottom vs 1× at top (mean-reversion + trend).

**Test on baselines:**

- BTCUSDC_LONG 20.16 final: STDEV 4 POS implies sizing edge at bottom helped — D 10× captured 4h dip better than 4×. Expected +2-3 points if D_MAX 10 default vs 4 for crypto trending.
- SNDK: STDEV delta -17 (loss) with D_MAX 10 — for that choppy stock, 10× over-leverages bottom wick → hurt. So per-category again: crypto D_MAX 10, stocks D_MAX 4-6.
- **DD:** Larger D_MAX raises DD at bottom entries (e.g., SNDK DD 6.36→9 if 10×). Need clip `MIN 0.5 MAX 2.5` already — but 10× is within clip.

**Settings:** Keep current 15-row STDEV sheet, but change defaults: `STDEV_SLOPE_LOOKBACK_D=180` (not 84), `STDEV_SLOPE_SIZING_D_MAX=10` for crypto_long, `6` for stocks_long. Add `STDEV_SLOPE_SIZING_15M_MAX=1.0` for stocks (tighter intraday).

**Function mod:** in `v12_quick_engine.py` `compute_regime_sizing_mult` verify `_stdev_max_map` already {'D':10,'4h':4,'1h':2,'15m':1.5} — correct, just need template default alignment.

**Worth adding? MAYBE — low priority.** n=1 evidence weak, need 365D walk-forward before committing. Keep existing sheet, tune lookback only.
